## 프로젝트 맥락

대형 행사 뒤 이동 시간이 평소보다 길어진 경험에서 시작한 개인 프로젝트입니다. 단순히 사람이 많이 모였다는 설명에서 멈추지 않고, 이동 수요와 대중교통 공급 proxy를 함께 확인했습니다. 교내 데이터 분석 프로젝트 우수상을 받았습니다.

## 분석 질문

여의도 불꽃축제 당일 수요는 언제, 어느 방향에 집중됐는가? 관측된 수요와 이동시간의 관계를 실제 운영 검토에 쓸 수 있는 차량 규모로 어떻게 바꿀 수 있는가?

초기 졸업 연구에서는 2023년 10월 7일 행사일과 6개 비행사 일요일의 OD 이동량과 체류인구를 시간대별로 맞췄습니다. 당시 노트북에는 비교일을 토요일로 적었지만 날짜를 다시 확인한 결과 모두 일요일이었습니다. 따라서 공개본은 이를 인과적인 행사 효과가 아닌 탐색적 주말 참고선 비교로 다룹니다. 분석 결과는 모든 목적지로 직접 운행하는 대신 공덕·당산·노량진 환승거점까지 연결하는 셔틀 시나리오로 이어졌습니다.

## 데이터 품질과 문제 재정의

초기 정류장 ID matching coverage는 약 `26.7%`였습니다. 이 상태로는 정류장 단위 결과를 신뢰하기 어려워 bbox, 정류장명, stop list, route master, TPSS와 GIS encoding을 다시 확인했습니다. 이 과정은 모델 선택보다 먼저 해결해야 할 데이터 품질 문제였습니다.

처음에는 행사 혼잡을 수요 증가만으로 설명하려 했습니다. 원 분석의 공통 정류장 비교에서는 행사일 승객 수가 비행사 일요일 평균보다 `49,566.667` 많았고, 정차횟수 proxy는 `3,487.667` 적었습니다. 18~23시에도 각각 `+32,627.667`, `-3,610.333`의 방향이 유지됐습니다. 이 값은 행사 효과의 인과 추정치가 아니라, 수요 증가와 공급 proxy 감소를 함께 살펴보게 만든 탐색적 관측입니다.

원 수치는 현재 합성 sample pipeline에서 다시 산출되지 않습니다. 공개본에서는 분석 흐름과 날짜·수단 비교 오류를 수정한 코드만 재현하며, 원 데이터 재확보 전에는 위 수치를 model performance로 사용하지 않습니다.

## 공개 범위

이 저장소에는 초기 탐색 노트북을 검토한 뒤 다시 작성한 전처리·비교·검증 코드와 공개용 노트북이 들어 있습니다. 원천 데이터는 이용 조건과 용량 문제로 배포하지 않습니다. 대신 열 구조를 맞춘 합성 샘플로 전체 실행 흐름과 테스트를 확인할 수 있습니다.

| 구분 | 공개 상태 |
|---|---|
| 전처리와 시간대별 집계 | 코드·테스트 공개 |
| 행사일과 비행사 참고일 비교 | 코드·합성 샘플 공개 |
| 날짜 단위 모델 검증 | 코드·합성 샘플 공개 |
| 원본 OD·체류인구 데이터 | 미공개 |
| 졸업 연구 당시의 전체 결과 재산출 | 원본 데이터 재확보 후 가능 |
| 셔틀 규모 계산 | 코드 공개 |

합성 샘플의 수치와 그래프는 파이프라인 검증용입니다. 실제 축제 효과나 모델 성능으로 해석하지 않습니다.

## 분석 설계

| 판단 | 적용한 방법 | 이유 |
|---|---|---|
| 참고선 만들기 | 비행사 날짜별로 먼저 집계한 뒤 평균 | 특정 날짜의 관측량이 참고선을 지배하지 않게 하기 위해 |
| 이동과 체류 함께 보기 | OD와 체류인구를 같은 시간 단위로 정리 | 이동 방향과 현장 집중 시간을 함께 보기 위해 |
| 이동시간 계산 | 이동량 가중평균 | 통행량이 다른 OD 행을 단순 평균하지 않기 위해 |
| 지체 관계 추정 | Isotonic regression | 초과 교통량이 증가할 때 예측 지체가 감소하지 않게 하기 위해 |
| 성능 비교 | 날짜 전체를 제외하는 교차검증 | 같은 날짜의 관측치가 학습과 평가에 함께 들어가는 누수를 막기 위해 |

선형 회귀는 초과 교통량과 이동시간 차이의 증가 폭을 하나의 기울기로 표현합니다. Isotonic regression은 증가 폭을 고정하지 않고 관계가 감소하지 않는다는 조건만 둡니다. 이 선택은 교통량과 지체의 인과관계를 증명하지 않습니다. 실제 검증에서는 동일 OD·수단끼리 비교해 이동 구성 변화와 지체를 분리해야 합니다.

초기 노트북에서 무엇을 수정했는지는 [노트북 검토 기록](docs/NOTEBOOK_AUDIT.md)에 적었습니다.

## 실행 방법

Python 3.10 이상에서 실행합니다.

```bash
python -m pip install -e ".[dev]"
pytest
python scripts/run_sample_analysis.py
```

스크립트는 다음 파일을 `results/sample/`에 만듭니다.

- `event_vs_baseline.csv`: 행사일과 비교일의 시간대별 차이

- `out_of_fold_predictions.csv`: 각 날짜를 제외하고 예측한 값
- `scenario_summary.json`: 셔틀 수송 용량 계산

## 운영 시나리오

졸업 연구에서는 약 13,000명의 추가 수요를 운영 규모 산정의 입력값으로 사용했습니다. 이 값은 현재 공개된 합성 파이프라인에서 다시 산출한 결과가 아닙니다.

모든 귀가 목적지로 노선을 만들면 차량 회전이 느려집니다. 그래서 행사장과 가깝고 서로 다른 철도 방향으로 갈아탈 수 있는 세 거점을 검토했습니다.

| 거점 | 분산 방향 |
|---|---|
| 공덕 | 서북권·공항철도·도심 |
| 당산 | 서부권·2호선·9호선 |
| 노량진 | 남부권·1호선·9호선 |

```text
45 seats × 100 buses × 3 rotations = 13,500 passenger movements
```

약 5천만원은 당시 차량 규모를 비교하기 위해 계산한 개략 비용입니다. 기사와 통제 인력, 승하차 공간, 회송 거리, 조달 방식은 포함하지 않았습니다.

## 해석 범위

- 행사일 한 번의 관측만으로 일반적인 행사 효과를 추정할 수 없습니다.
- 행사일은 토요일이고 참고일은 일요일이라 요일 차이가 섞여 있습니다.
- 참고일의 날씨, 도로 통제와 다른 행사는 현재 공개 데이터에서 통제하지 못했습니다.
- 현재 시간대별 평균 이동시간에는 출발지 구성 변화가 섞일 수 있습니다. 지체 분석에는 동일 OD·수단 단위 재검증이 필요합니다.
- Isotonic regression은 단조 관계를 표현하지만 인과 효과를 추정하지 않습니다.
- 공개 샘플은 코드 검증용 합성 데이터이며 실제 성능 근거가 아닙니다.
- 셔틀 계산은 수송 가능 규모를 비교하는 산술 시나리오입니다. 배차와 도로 운영 효과를 검증한 simulation은 아닙니다.

남은 검증 항목은 [후속 분석 계획](docs/LEARNING_ROADMAP.md)에 정리했습니다.

## 기여

실생활에서 느낀 이동 불편을 분석 질문으로 바꾸고, 원천 데이터 선택과 결합, 정류장 matching 재검산, 시간대별 비교, 단조 제약 모델, 환승거점과 차량 규모 산정까지 진행했습니다. 공개본에서는 초기 탐색 코드를 함수와 테스트 단위로 다시 나누고, 재현할 수 있는 범위와 아직 검증하지 못한 주장을 분리했습니다.
